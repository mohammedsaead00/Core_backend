## Goal

Close the API coverage gap: expose the 3 read views and add the missing write endpoints so every Flutter screen has a backend, using only existing schema (no migrations needed). All endpoints follow the established conventions (JWT-derived user id, `OwnDataOrActiveCoach` policy for coach views, problem-details errors, camelCase JSON).

## 1. Insights endpoints (the 3 views, currently unmapped in HTTP)

- `GET /api/me/personal-records` — own rows from the `personal_records` view via the existing `PersonalRecords` DbSet
- `GET /api/me/weekly-progress?weekStart&limit` — `weekly_progress` view
- `GET /api/me/weight-progress?limit` — `weight_progress` view
- `GET /api/coach/clients/{clientUserId}/personal-records` — policy-guarded (same `OwnedResource` + `AuthorizeAsync` pattern as the other coach views)

## 2. User-side write endpoints

- **Daily activity (Health Connect ingest):** `GET /api/me/daily-activity?date`, `POST` (create), `PUT /{id}` (update own) — mirrors prod RLS (own CRUD minus delete)
- **Weekly activity (charts):** `GET ?weekStart`, `PUT` (upsert by weekStart+dayIndex — no unique constraint in prod, app-managed upsert)
- **Exercise progress:** `GET ?sessionId&date`, `POST` (create own)
- **User programs:** `GET`, `POST`, `PUT /{id}`, `DELETE /{id}` (full own CRUD per prod RLS)
- **Barcode scan history:** `POST` (record a scan; barcode now nullable — no FK), `GET ?limit`

## 3. Coach-side endpoints (dashboard + content flows)

- `GET /api/coach/clients` — the dashboard client list (active subscriptions ⋈ profiles), which the original `coach_dashboard_repository_impl` reads from `subscriptions`
- **Coach content:** `GET /api/coach/content`, `POST`, `PUT /{id}`, `DELETE /{id}` (own via `coaches.user_id`); client read: `GET /api/coaches/{coachId}/content` returns `is_public` OR assigned-to-caller items (matches prod RLS)
- **Assignments:** `POST /api/coach/assignments` (coach → client + content), `GET /api/coach/assignments`, `GET /api/me/assignments` (client view incl. content info)
- **Subscription phases:** `GET/POST /api/coach/subscriptions/{id}/phases`, `PUT/DELETE /api/coach/subscriptions/{id}/phases/{phaseId}` (coach manages via subscription ownership); client read `GET /api/me/subscriptions/{id}/phases`
- **Coach onboarding:** `GET` + `PUT` (upsert own `coach_onboarding` row)
- **Subscriptions without Stripe:** `POST /api/coach/subscriptions` (coach creates a subscription for a client, default `pending`), `PATCH /api/coach/subscriptions/{id}/status` → reuses `ISubscriptionLifecycleService.ProcessSubscriptionStatusAsync` (so conversation + client counting + CHECK constraints all apply)

## 4. Hot-path hardening (small)

- `ClientAccessService`: cache `IsActiveClientOfCoach` results in `IMemoryCache` for 60 s (the auth handler runs on every coach request); invalidated naturally by expiry — acceptable for the "coach lost access" window and matches dashboard usage.
